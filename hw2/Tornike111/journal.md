### Week 5 · Tool Contract
**Where I used it:** `rank_loyal_fans`, contract class `RankLoyalFans` in `src/contracts.py`, product pull request #13, golden cases in `evals/tools/Tornike111.yaml`. Before that I reviewed Murman's tool frame in #9 and ran its tests on my Windows machine, where `tests/test_mcp.py::test_both_doors_send_the_same_refusal` failed because my `pydantic` 2.13 ordered the errors differently from CI. **What I noticed:** in my red run (#14, `operator_only=False`) I expected golden case `a1` to fail because fan data leaked. It did not leak: my own backstop inside the tool refused the anonymous caller. The case failed because the tool was *offered* at all. So the lock I thought was protecting fan data (the registry) was not the only one, and without the test I would not have known which one was doing the work. **Do differently:** write the "anonymous caller" and "identity in the arguments" cases before asking the agent for the tool, and run every test suite on my own machine before approving, not just trust CI.

### Week 6 · Session State
**Where I used it:** not built yet. The closest thing FanReserve keeps is `data/attendance.json`: who went to which category of event, and when. It should be readable by operators only (as `rank_loyal_fans` already is), stored under pseudonymous ids, and kept for only as long as the rule uses it: `rank_fans()` ignores every visit older than `LOYAL_WINDOW_DAYS = 90`. **What I noticed:** `fan-0006` and `fan-0018` in my test data have football visits from March to July that can never count, yet we still store them. A lifetime is not a separate decision from the rule: the 90-day window already says how long attendance is worth keeping. **Do differently:** when I design a data file, write down its scope (who may read it) and its lifetime (when a row is deleted) on the first day, next to the rule that reads it.

### Week 7 · Supervised Autonomy Loop
**Where I used it:** the loop in `src/act.py` (`MAX_ROUNDS = 3`). The goal for the operator agent (spec slice 6) is "review this week's events and propose which ones hold seats, and for whom". It would call `check_reserve` for each event and `rank_loyal_fans` for the category. Neither needs a yes, because both only read, and the contracts say so ("Effect: reads", "Idempotent: yes"). The one tool that must wait for the operator's yes is a future `place_hold`, which does not exist yet. **What I noticed:** when I asked through the MCP door, the model answered with the five fans and added on its own that nothing was reserved or sent. That sentence is only true because no tool can reserve anything. Today the safety comes from what we did not build, not from a confirmation step. **Do differently:** build `place_hold` together with its confirmation gate and a test that it does nothing without a yes, instead of adding the tool first and the gate later.
